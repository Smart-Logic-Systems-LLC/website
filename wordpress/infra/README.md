# infra — WordPress on an Azure VM as a Podman quadlet

Deploys the block theme in `../wp-content/themes/sls` to a single Azure VM, modelled
on the Drupal site's `drupal-website/infra` (Smart-Logic-Systems-LLC/graveyard):
OpenTofu creates the resource group and VM, Ansible installs Podman and runs the
site as a Kubernetes manifest through a quadlet (`/etc/containers/systemd/slswebsite.kube`).

| Environment | Resource group | URL |
| --- | --- | --- |
| dev | `slswebsite-dev-vm_k8s_quadlet` (North Central US) | https://dev.smartlogicsystems.com |

## Prerequisites

- [Azure CLI](https://learn.microsoft.com/cli/azure/), signed in: `az login` (the
  subscription is the CLI's default; no service principal needed)
- [OpenTofu](https://opentofu.org/docs/intro/install/)
- [uv](https://docs.astral.sh/uv/) (installs Ansible into `.venv`)
- GNU Make, `rsync`, `curl`, `openssl`

## Usage

Run `make` in this folder to list the targets. From the repo root, prefix them
with this folder's path, so `make https` here is `make wordpress/infra/https`
there. Variables work the same way: `make wordpress/infra/deploy APPROVE=1`.

```sh
make deploy          # Azure resources + site (asks before changing Azure; APPROVE=1 skips)
make https           # once DNS points at the VM: get the certificate, verify HTTPS
make login           # verify the wp-admin login over HTTPS and print it
make app-deploy      # site only: theme, config, WordPress install/seed
make status          # service, containers, memory
make logs            # journal of the slswebsite service
make ssh             # shell on the VM; CMD='...' runs a command
make check           # tofu fmt/validate + ansible-lint
```

`ENV=<env>` selects `deployment/vm/azure/<env>.tfvars` and `env/<env>.yml`
(default `dev`).

**First deploy of an environment.**

1. Run `make deploy`. Besides the VM, it creates an Azure DNS zone for the
   site's subdomain (`dns_zone` in `<env>.tfvars`) holding its A and mail records.
2. Run `make dns`. Until the subdomain is delegated it lists what to change at
   GoDaddy: remove the subdomain's A record and add one NS record per Azure
   nameserver. Re-run it until it passes. The root domain stays at GoDaddy.
3. Run `make https`. It checks public DNS first, then has Caddy request the
   certificate and waits until the site serves it, so it is safe to re-run.
4. Run `make login`. If someone changed the password in wp-admin, run
   `make login RESET_PASSWORD=1` to set it back to the stored one.

**Mail.** WordPress sends through a Postfix relay container in the pod, which
hands mail to Azure Communication Services Email (Azure blocks outbound port 25
from VMs). The sender is `wordpress@<dns_zone>`; the zone holds its SPF and DKIM
records. After `make dns` passes:

1. Run `make email-verify` to have Azure verify the sending domain.
2. Set `email_domain_verified = true` in `deployment/vm/azure/<env>.tfvars` and
   run `make deploy`. This adds the relay container.
3. Run `make mail-test` (`TO=<address>`; default your Azure login).

**Content.** The first deploy installs WordPress and creates the pages from the
theme's patterns. Later deploys keep page content edited in wp-admin;
`make app-deploy RESEED=1` resets the pages to the patterns. Theme files are
bind-mounted read-only, so `make app-deploy` makes theme changes live without a
restart.

**Tear down.** `make app-destroy` removes the site, database and uploads from the
VM. `make infra-destroy` deletes the whole resource group.

## How it runs

```
Internet ─▶ NSG (80, 443; 22 from the deployer's IP) ─▶ VM Standard_B2pts_v2, Ubuntu 26.04 LTS arm64
  systemd: slswebsite.service  (quadlet → podman kube play /opt/slswebsite/deployment.yml)
    pod slswebsite-pod
      caddy      :80/:443  automatic Let's Encrypt certificate, reverse proxy
      wordpress  :8080     wordpress:7.1.2-php8.3-apache, theme mounted read-only
      db         :3306     mariadb:11.8
      relay      :587      Postfix → Azure Communication Services Email (once mail is set up)
    volumes: slswebsite-{wp-data,db-data,caddy-data,caddy-config,mail-spool}
DNS: GoDaddy (root domain) ─NS─▶ Azure DNS zone for the subdomain (A, SPF, DKIM)
```

## Differences from the Drupal deployment

- **Region:** North Central US. Central US has no `Standard Bpsv2 Family` vCPU
  quota left (prod uses both vCPUs); the VM size is the same.
- **OS:** Ubuntu 26.04 LTS. Prod's Ubuntu 25.10 image is end-of-life (July 2026).
- **Authentication:** OpenTofu authenticates with the Azure CLI session instead of a
  client secret.
- **TLS:** Caddy terminates TLS in the pod. Apache's `mod_md`, used by prod, needs
  an Apache restart to load a new certificate (see the graveyard TODO).
- **Images:** stock images are used. The theme is synced to the VM and
  bind-mounted, so no image registry is needed.
- **Secrets:** generated by Ansible into `secrets/<env>/` (gitignored); nothing
  secret is committed. This repository is public.
- **SSH:** the SSH rule allows only the deployer's current public IP. Re-run
  `make infra-deploy` after your IP changes.
- **Search engines:** the dev site sends `X-Robots-Tag: noindex` and WordPress
  "discourage search engines" is on (`noindex` in `env/dev.yml`).

## Local files (gitignored)

| File | Holds |
| --- | --- |
| `deployment/vm/azure/dev.tfstate` | OpenTofu state, **including the VM's SSH private key**. Losing it means managing the resources by hand. |
| `deployment/vm/azure/dev.pem` | SSH key for `slsadmin@<ip>` |
| `deployment/vm/azure/dev.inventory.ini` | Ansible inventory (written by OpenTofu) |
| `secrets/dev/` | Database and wp-admin passwords; `smtp.yml`, the relay's Azure SMTP credentials |
| `.known_hosts` | The VM's SSH host key |
